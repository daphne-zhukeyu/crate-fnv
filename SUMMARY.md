# fnv 1.0.7: verification status report (2026-11-04)

## Summary 

Specs and proofs generated by Claude verify 4 of the crate's 4 functions (`default`, `with_key`,
`finish`, `write`); the remaining public items are three type aliases with no code. The trusted
base is empty: `verus --no-cheating` passes with no flagged item. No upstream bug was found. One
documentation gap: the crate never says which FNV variant it implements (it is 64-bit FNV-1a; the
docs say only "Fowler–Noll–Vo"), and the hash of integers written through `write_u32` etc. is
endianness-dependent, which the docs don't mention.

A hand-written gold spec of the public API was compared with Claude's spec as Verus refinement obligations in both directions,
with Claude writing the linking proofs. The two specs cover all 4 functions; Claude's spec implies
the gold spec for 4 of 4, and the gold spec implies Claude's for 4 of 4. The two specs are
equivalent on the whole API.

A code-change detection script compares the upstream and annotated crates after macro expansion
(which erases the ghost code) and flags every trusted/unsafe marker; each finding needs human
sign-off. It found 3 changes and 0 trusted markers. Claude's proposed classification is that all 3
are ghost-only residue (imports, an empty module, an empty trait impl, `{}` no-op blocks); the only
MIR difference in `write` is a scope display name.

Claude Code spent about 25 s from first writing the spec to a full pass (7 verified), about 2
minutes on spec-and-proof work in total, and about 6 minutes on fnv overall including negative
controls, builds and the write-up.

## Spec comparison notes

- Gold spec frozen as `spec_compare/human_written_spec.v1.rs`. Claude's only
  edit to the working copy is in the `vectors()` proof fn: `let initial = default_result()` was
  inlined into the asserts, because `by (compute)` treats a `let`-bound variable as symbolic and
  the residue sent the SMT solver over its resource limit. No definition changed.
- The two state models coincide (the `u64` hash word), so the links are direct; `write` needs one
  induction (`lemma_fold_agree`) showing the two folds are the same function.
- Both specs make the same choices on the open points: FNV-1a order, `with_key` as the raw state,
  first byte first, multiply modulo 2^64.

## Caveats

- "Verified" means the code meets Claude's spec. The spec's correctness rests on the published
  FNV-1a test vectors it reproduces and on its equivalence with the independently written gold spec.
- The contracts are on `impl Hasher for FnvHasher`. vstd gives the `Hasher` trait itself no
  specification, so code generic over `H: Hasher` (for example `HashMap`) does not see them.
- `write_u8`, `write_u32`, … are std's default methods and are outside the verified surface.
